App transfer between boxes

Move a running app from one server to another — even when the two boxes run different edges (kamal-proxy vs Caddy). The unlock is dedicated, runtime-wired database containers so an app's state is a self-contained, portable unit.

Pillar: Runtime backends Priority: P1 Effort: L Status: Decisions locked · ready to build

Problem

"Move a workload between boxes" is the essence of fleet management, but today it's a manual, forensic exercise. The primitives already exist — deploy-to-server, DatabasePull (pg_dump→scp→restore), CaddyClient, CloudflareClient (DNS), and per-server edge_type. Two things are missing:

  • Orchestration — no first-class, staged "move app A→B" with a dry-run and rollback.
  • State coupling — the database is welded to the box (a shared cluster), so one app's data can't move as a unit.

The core bet: dedicated, runtime-wired database containers

Give each app its own Postgres container (its own volume), and inject the app's DB config at runtime (Hatchbox-style: it writes database.yml at boot; the DB is a separate container). The image carries no DB coordinates — so the same image runs against whatever endpoint it's pointed at. An app's state becomes a self-contained unit (<app>-db container + volume); moving the app = move/replicate that one unit and re-inject the endpoint.

This diverges from today's shared cluster (one Postgres, a DB+role per app) which trades portability for density.

Two axes: isolation × locality (both per-app)

Mode is isolation (shared cluster vs dedicated container). Independently, placement is locality — is the DB on the app's own box, or on a separate machine dedicated to databases? Both are per-app knobs, and Conductor must let you switch between them live.

mode × placementcolocated (app's box)dedicated DB host (separate box)
shared clusterDense fleet — today's defaultCentral DB server serving many apps
dedicated containerIsolated, on the app's boxIsolated, on a DB-dedicated box

Switching is first-class. Converting an app's DB between any two cells — e.g. calm.page: shared-cluster-colocated → dedicated container, on-box or onto a dedicated DB host — is the same provision → replicate → cut-over → decommission machinery as a full app transfer, scoped to the database only. So it's reusable both standalone ("give this app its own DB / move its DB to the DB box") and as a step inside a whole-app box transfer.

The edge is pluggable (kamal-proxy vs Caddy)

Conductor already stores Server#edge_type (caddy / kamal_proxy / other / none). A transfer doesn't need the boxes to match — it needs Conductor to render the destination edge's config. Introduce an edge adapter:

Edge.for(server).publish(domain:, upstream:) → CaddyAdapter (Admin API, exists as CaddyClient) or KamalProxyAdapter (deploy.yml / proxy config — the missing half).

Once both exist, "publish this app's domain on box B" is uniform regardless of B's edge. Converges with slot 18 (per-app proxy mode) and slot 22 (Caddy console).

✅ Decision C — RESOLVED (operator, 2026-07-26)
Build the KamalProxyAdapter — transfers publish into either edge via Edge.for(server).publish(...); Caddy is not forced on receiving boxes.

The transfer workflow

An app is tied to a box across orthogonal axes; a transfer reconciles each, staged for minimal downtime:

  1. Plan / dry-run — emit exactly what will change: compute (redeploy to B), edge (A's config → B's edge translation), database (mode + migration method), DNS (repoint). No mutation — this is the "make sense of it" artifact.
  2. Stand up on B (parallel) — deploy the app to B (Kamal builds on B over SSH); provision <app>-db on B if dedicated. A stays live.
  3. Replicate state — dedicated: base-backup/restore or logical replication into B's DB container; shared: DatabasePull A→B.
  4. Cut over — publish the domain on B's edge, repoint DNS (CloudflareClient for CF domains), let B's edge mint TLS; final DB sync + switch DATABASE_URL.
  5. Verify + drain — health + site_check through B; stop A after a hold window; keep A's DB as a rollback snapshot for N days.
✅ Decision D — RESOLVED (2026-07-26)
Ship cold-cutover first (dump/restore in a maintenance window); add near-zero logical replication as a follow-up.

Acceptance criteria

  • A dry-run emits the full change set (compute / edge / DB / DNS) with zero mutation.
  • An app moves A→B across different edges (kamal-proxy → Caddy) with its domain + TLS working on B.
  • A dedicated-DB app's state moves as a self-contained unit; DATABASE_URL is injected, never baked into the image.
  • An app's DB converts standalone between mode/placement cells (e.g. shared-colocated → dedicated container on a DB host) with the app re-pointed and the old DB retained for rollback.
  • Rollback at any step before decommission points DNS/edge back to A with no data loss.

Open questions — ✅ resolved (operator, 2026-07-24…26)

  • Port/socket allocation — non-issue by default: each <app>-db joins the app's Docker network, reached by container DNS (…@<app>-db:5432), so N dedicated Postgres coexist on one box with no host-port collision. Host ports / Unix socket are opt-in, only for external psql/backup access.
  • Backups — reuse the existing R2/S3 destination choice, one schedule per <app>-db. No new backup surface.
  • PG major-version A↔B — not blocked; dump/restore across versions (the client-version rules DatabasePull already applies).
  • Clone — the same transfer pipeline with a stop-gap: provision → replicate → cut-over, then HOLD before drain/decommission, leaving A live.
