SES email observability

Event-level SES truth built into Conductor: every delivery, bounce, complaint, open, and click — per message, per recipient — ingested from SNS and tied to the App/Domain that sent it. The flight recorder that complements slot 20's sending-health gauges.

Pillar: Provider automation Priority: P1 Effort: M Status: Draft · annotate

Problem

Conductor injects SES SMTP creds at deploy, so the fleet sends mail — but has zero visibility into what happens after send.

Slot 20 (SES + SNS messaging) covers the aggregate gauges: reputation, bounce/complaint rates, verified identities. This is the complementary event stream — "what happened to this email, to this recipient?" — the layer people otherwise pay a glorified-SES-wrapper SaaS for. Owning it keeps the fleet on raw SES with a single pane of glass in the control plane.

Slot 20 = the dashboard gauges (rates, reputation). This = the flight recorder (every event, searchable, per message).

Design reference: Sessy

We adapt the model (not the codebase) of Sessy — a clean, battle-tested open-source SES observability app (Marc Köhlbrugge, Fizzy-inspired; O'Saasy License, reference only). We mirror its proven shape:

  • SesEventPayload — a PORO that parses one SES event JSON. Ported near-verbatim; it encodes SES's payload quirks (recipients live under bounce/complaint/delivery/… per type).
  • Idempotent ingest — find-or-create a message by ses_message_id, then create-or-find an event on (ses_message_id, event_type, recipient, event_at).
  • Raw webhook record for idempotency + replay; SNS signature verification (Aws::SNS::MessageVerifier, cached — a fresh verifier re-downloads the signing cert ~600ms/req) with auto-confirm of SubscriptionConfirmation; a retention policy.

Event types: Send · Delivery · Bounce (Permanent/Transient/Undetermined) · Complaint · DeliveryDelay · Reject · Rendering Failure · Open · Click · Subscription.

Data flow

  1. SES config-set publishes events → SNS topic → POST /webhooks/ses/:token.
  2. Ses::WebhooksController resolves the MessageStream by token, verifies the SNS signature, auto-confirms SubscriptionConfirmation.
  3. On Notification: persist a SesWebhook (idempotent) + enqueue processing.
  4. SesWebhook#process → SesEventPayload → find-or-create EmailMessage → ingest an EmailEvent per recipient.
  5. Map to App: config-set→App binding first, else sender-domain→Domain→App. Unmatched events still ingest (org-scoped, app_id nil) — nothing lost.
Decision A — model home
Is the tokened webhook target a new MessageStream model, or does it hang off Organization (one SES ingest URL per org) or Domain? Proposed: a lightweight MessageStream (name + token + optional app/config-set + retention), so an org can run several (one per config set).
Decision B — ingest sync vs async
Verify + persist the SesWebhook synchronously (fast 200 to SNS), then parse/ingest events in a Solid Queue job? Proposed: async — SNS retries on non-2xx, cert-verified persist is cheap, and parsing/mapping shouldn't block the webhook.
Decision C — open/click tracking
Opens/clicks require SES config-set open/click tracking enabled (adds a tracking pixel / link redirect). Ingest them whenever present — but should auto-wiring enable tracking? Proposed: ingest always; enabling tracking is an explicit opt-in (privacy).
Decision D — retention default
N days before auto-delete. Proposed: 30 days, per-MessageStream override (Sessy-style).

Auto-wiring — don't make the operator hand-configure SNS

Building on slot 20's SES-manage client, offer "observe this app's email": create/confirm an SNS topic, point the SES config-set's event destination at it, subscribe Conductor's /webhooks/ses/:token URL, and store the MessageStream — one action, mirroring put_behind_cloudflare's one-button ergonomics. Manual setup (paste the webhook URL into SES) stays supported.

Surface

  • UI — a deliverability view: per-App/Domain rates (delivery/bounce/complaint), a reverse-chronological event stream, search by recipient/subject, date + type filters. A message detail page = the timeline of its events.
  • MCP — conductor_read action=email_events (filter by app/domain/type/date; search) so agents can answer "why did mail to X fail?" Feeds situation reads.
  • Alerts — bounce/complaint rate over threshold → the alerts pipeline, complementing slot 20's aggregate reputation alert.

Implementation slices

  1. Ingest core — SesEventPayload (port), EmailMessage/EmailEvent/SesWebhook models + migrations, idempotent org-scoped ingest. Unit-tested against real SES payload fixtures.
  2. Webhook endpoint — Ses::WebhooksController: aws-sdk-sns verifier (cached), subscription auto-confirm, async processing job.
  3. App/domain mapping — config-set→App + sender-domain→Domain resolution; backfill app_id.
  4. Surface — deliverability UI (rates + stream + search/filter) + conductor_read action=email_events + message detail.
  5. Auto-wiring — provision SES config-set event destination → SNS → webhook from the SES-manage flow; retention job + threshold alert.

Acceptance criteria

  • A real SES SNS notification is signature-verified, ingested idempotently (replaying it creates no duplicates), and appears in the UI + over MCP within seconds.
  • Events attribute to the correct App/Domain; unmatched events still ingest (org-scoped, app_id nil) and are visible.
  • An operator sees per-app delivery/bounce/complaint rates and can search a recipient/subject to a message's full event timeline.
  • Auto-wiring configures SES→SNS→Conductor end-to-end from one action; manual setup still works.
  • Events past the retention window are auto-deleted; a bounce/complaint-rate threshold fires an alert.
