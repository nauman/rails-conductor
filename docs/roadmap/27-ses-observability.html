SES email observability

Event-level SES truth built into Conductor: every delivery, bounce, complaint, open, and click — per message, per recipient — ingested from SNS and attributed to the App/Domain that sent it. The flight recorder that complements slot 20's sending-health gauges.

Pillar: Provider automation Priority: P1 Effort: M–L Status: Draft · annotate

Problem & the shape of the answer

Conductor injects SES SMTP creds at deploy, so the fleet sends mail — but goes blind the instant an email leaves the box.

Slot 20 owns the aggregate gauges (reputation, bounce/complaint rates, identities) polled from the SES API. This plan owns the event stream: SES → SNS pushes one JSON notification per lifecycle event, and we turn that firehose into "what happened to this email, to this recipient, and which app sent it." Slot 20 is the speedometer; this is the black box.

Non-goals: we are not building a mail sender (apps still send via SES directly), not an inbound-mail parser, and not re-implementing slot 20's aggregate SES-API stats. This plan is strictly the outbound event ingestion + attribution + query layer.

Direction — the key architectural choices

Three decisions define the whole build; getting them right is why this is a plan and not a widget:

1 · Config-set event destinations, not identity notifications

SES has two SNS paths. Legacy identity notifications (SetIdentityNotificationTopic) emit only bounce/complaint/delivery. Configuration-set event destinations emit the full set incl. open/click/deliveryDelay/reject. We use config sets — the richer, modern path.

2 · A default config set per identity, so apps don't change their code

SES only emits events for a send if that send carries the config-set (header X-SES-CONFIGURATION-SET or the API param). We do not want to patch every app's mailer. SES v2 PutEmailIdentityConfigurationSetAttributes sets a default config set on the domain identity — every message from that domain then emits events with zero app changes. This is the unlock that makes "observe this app" a one-click Conductor action.

3 · Attribution by a deterministic config-set name, domain as fallback

Name the config set conductor-<app-slug> and store the binding on ingest, so every event maps to its App deterministically. Fall back to matching source_email's domain against a Conductor Domain for mail sent outside the managed config set. Unmatched still ingests (org-scoped, app_id nil).

Data model (concrete)

Adapted from a proven open-source SES-observability schema, made org-scoped and app-attributed. Four tables + one PORO.

# message_streams — the tokened ingest target
organization_id  bigint   not null
name             string   not null
token            string   not null   # UUID → webhook URL; unique
config_set_name  string              # conductor-<slug>, for attribution
app_id           bigint              # default attribution target
retention_days   integer             # nil = keep forever
index (token) unique · index (organization_id)

# email_messages — one email
organization_id  bigint   not null
app_id           bigint              # resolved on ingest, may be nil
ses_message_id   string   not null   # unique per org
source_email · subject · sent_at · mail_metadata(json) · events_count(counter)
index (organization_id, ses_message_id) unique · index (app_id) · index (sent_at)

# email_events — one event, one recipient
organization_id · app_id · email_message_id(fk) · ses_webhook_id(fk)
event_type       string   not null   # enum: send/delivery/bounce/…
recipient_email  string   not null   # normalized lower/strip
event_at         datetime not null
bounce_type      string              # Permanent/Transient/Undetermined
event_data(json) · raw_payload(json)
# THE dedup key — idempotency lives here:
index (ses_message_id, event_type, recipient_email, event_at) UNIQUE
index (app_id, event_at, event_type) · index (recipient_email) · index (event_type)

# ses_webhooks — raw SNS envelope, idempotent processing
organization_id · sns_message_id(unique) · sns_type · sns_timestamp
raw_payload(json, not null) · processed_at
index (sns_message_id) unique · index (processed_at)

SesEventPayload (PORO, ported): parses one SES event JSON — event_type, mail.messageId, per-type recipients (they live under bounce/complaint/delivery/… not a single field — SES's quirk), per-type timestamp, and event_data.

Ingestion pipeline

POST /webhooks/ses/:token
  → resolve MessageStream by token (404 if unknown)     # tenant boundary
  → Aws::SNS::MessageVerifier (cached instance).authentic?  # reject forgeries
  → case sns["Type"]
      SubscriptionConfirmation → confirm ONLY if TopicArn ∈ org's SES account
      Notification             → SesWebhook.create_or_find_by!(sns_message_id:)
                                 return 200 immediately  # Decision B: async
                                 enqueue Ses::IngestJob(webhook)
      UnsubscribeConfirmation  → log, 200

Ses::IngestJob(webhook):
  return if webhook.processed_at?                         # idempotent replay guard
  payload = SesEventPayload.new(JSON.parse(sns["Message"]))
  msg = EmailMessage.find_or_create_by!(org, ses_message_id: payload.message_id) { … }
  payload.recipients.each { EmailEvent.create_or_find_by!(dedup_key) { … } }  # unique index = truth
  resolve_app!(msg)   # config_set_name → app_id, else source_email domain → Domain → app
  webhook.mark_processed!

Idempotency is enforced at the DB, not in Ruby: replaying a webhook (SNS delivers at-least-once) hits the unique ses_webhooks.sns_message_id and the unique event dedup key, so re-processing is a no-op. Ordering is not assumed — a Delivery can arrive before its Send; the message is find-or-created either way, and a message's "current status" is computed from its events, never stored as a mutable field.

Auto-wiring — one action, five AWS calls

"Observe this app's email" (UI button / MCP), building on slot 20's SES client. Idempotent — safe to re-run:

1. CreateConfigurationSet            name = conductor-<slug>
2. CreateTopic (SNS, standard)       name = conductor-ses-<slug>   # NOT fifo
3. Subscribe                         protocol=https, endpoint=/webhooks/ses/<token>
                                     RawMessageDelivery = false      # keep the SNS envelope
4. CreateConfigurationSetEventDestination  → SNS topic, MatchingEventTypes=[all]
5. PutEmailIdentityConfigurationSetAttributes  domain → default = conductor-<slug>

Step 5 is what makes it zero-touch for the app. Manual setup (operator pastes the webhook URL + config-set name) stays first-class for people who don't want Conductor holding the IAM keys.

Query & surface

A filter/search layer over events, scoped to app/org:

  • Filters — date-range presets (today … last 90 days, custom), event-type multi-select, bounce-subtype (permanent/transient/undetermined), plus filter_counts for the facet badges.
  • Search — LIKE over recipient email + subject (sanitized). Postgres ILIKE; a trigram index if volume warrants.
  • Deliverability rollup — per App/Domain: delivered / bounced / complained / opened / clicked counts + rates over the window.
  • Message detail — the event timeline for one ses_message_id.
  • MCP — conductor_read action=email_events (app/domain/type/date/search); a bounce spike feeds the situation read.

Unknowns & risks (the sharp edges)

R1 · SubscriptionConfirmation abuse
Auto-confirming any SubscribeURL lets an attacker point their SNS topic at our endpoint and flood it. Mitigation: confirm only when the message's TopicArn account id matches a connected SES credential in that org. Open: do we hard-require this, or allow manual approval for un-owned topics?
R2 · Signature-verifier SSRF + latency
Aws::SNS::MessageVerifier fetches the SigningCertURL; it must be pinned to AWS hosts (the gem does this) and the verifier instance shared (a per-request instance re-downloads the cert ~600ms — this dominates the endpoint's latency). Open: confirm the gem's host allowlist covers all SES regions we use.
R3 · Cross-tenant event injection
A valid AWS signature proves "from AWS," not "from this org's account." Without the TopicArn↔account check, org A could receive org B's events at a leaked token. Mitigation: same account-id check as R1, applied on every Notification, not just confirm.
R4 · Volume & retention
A busy sender is millions of events/month. a naive SQLite store won't do; Conductor is Postgres — good, but we need the retention job (delete_all by sent_at cutoff, batched) and to watch index bloat. Open: partition email_events by month, or is retention enough at fleet scale?
R5 · Open/click = tracking pixels + link rewriting
These events only exist if the config set enables open/click tracking, which injects a pixel and rewrites links through an SES redirect (a deliverability + privacy cost). Open: default OFF and opt-in per stream (Decision C).
R6 · Attribution gaps
Shared domains, subdomain senders, or mail sent without our config set → app_id nil. Acceptable (still ingested), but the rollups must make "unattributed" a visible bucket, not silently drop. Open: is the conductor-<slug> config-set convention enough, or do we also read the SES ses:configuration-set tag on the message?
R7 · We hold IAM keys to auto-wire
Steps 1–5 need SES/SNS write perms. Some operators won't grant that. Manual mode must be complete, not a second-class fallback.

Decisions to make (annotate here)

Decision A — model home
A dedicated MessageStream (an org can run several, one per config set/app) vs. hanging ingest off Organization (one URL/org) or Domain. Proposed: MessageStream — it maps 1:1 to an SES config set and carries the retention + app binding.
Decision B — sync vs async ingest
Proposed: verify + persist the SesWebhook synchronously (fast 200; SNS retries on non-2xx), parse/ingest in a Solid Queue job. Trade: a tiny lag before events appear, for a webhook that never times out under a burst.
Decision C — enable open/click tracking on auto-wire?
Proposed: ingest always, enable tracking never-by-default — per-stream opt-in, because it rewrites links + adds a pixel.
Decision D — retention default
Proposed: 30 days, per-MessageStream override, nil = keep forever.
Decision E — cross-account trust (R1/R3)
Proposed: hard-require the TopicArn account to match a connected SES credential before confirming or ingesting. Blocks the zero-config "just paste a URL" path for un-owned accounts — acceptable?
Decision F — default config set on the identity (zero-touch)?
Proposed: yes, set conductor-<slug> as the domain identity's default (step 5) so apps emit events without code changes. Risk: it overrides an identity-level default the operator may already rely on — detect & warn before overwriting.

Phased plan

  1. Ingest core (no network) — port SesEventPayload; EmailMessage/EmailEvent/SesWebhook/MessageStream models + migrations with the dedup unique index; idempotent org-scoped ingest. Driven entirely by captured SES payload fixtures — this slice needs no AWS.
  2. Webhook endpoint + security — Ses::WebhooksController, aws-sdk-sns shared verifier, subscription auto-confirm with the account-id check (R1/E), async Ses::IngestJob. Red-team tests: forged signature, wrong-account topic, replay.
  3. Attribution — config_set_name → app + source_email domain → Domain → app; backfill on ingest; "unattributed" bucket in rollups.
  4. Surface — deliverability rollup + event stream + filters/search (port Filterable/Searchable) + message-detail timeline + conductor_read action=email_events.
  5. Auto-wiring + lifecycle — the 5-call provisioner (idempotent), the default-config-set-on-identity step (F, with overwrite warning), retention job, bounce/complaint threshold alert into slot 12.

Test plan

  • Payload fixtures — one captured real SES notification per event type (send, delivery, bounce×3 subtypes, complaint, deliveryDelay, reject, renderingFailure, open, click, subscription). Assert SesEventPayload extracts recipients/timestamp/data for each — SES puts recipients in a different place per type, so this is the highest-value test.
  • Idempotency — POST the same notification twice → 1 SesWebhook, 1 message, N events; a second delivery with the same dedup key inserts nothing.
  • Ordering — deliver Delivery before Send → message + both events exist; computed status is correct.
  • Security — forged signature → 403; SubscriptionConfirmation/Notification from an un-owned TopicArn → rejected; unknown token → 404.
  • Attribution — config-set-bound app; sender-domain match; neither → nil app, still queryable.
  • Retention — events past the window are batch-deleted; counter caches stay consistent.
