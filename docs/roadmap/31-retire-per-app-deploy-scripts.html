Retire per-app deploy scripts

Every app deploys through Conductor. Three apps currently deploy via repo scripts Conductor never sees, so it holds no release record for them, can offer them no rollback, and — worse — presents a stale record as current truth.

Pillar: Runtime backends Priority: P0 Effort: M Status: Spec'd 2026-08-03

Problem

A control plane that does not perform the deploy does not know what is deployed — and says so anyway.

Conductor learns about a release when it performs the deploy. InventList, platepose and minimalnarrow are rolled by repo scripts and plain docker run, so Conductor's record for them is whatever it last saw, indefinitely.

This is not a cosmetic gap. On 2026-08-02 Conductor's newest record for app 13 was a failed deploy from 07-28 against the retired inventlist-mvps box. An audit took that SHA as its release baseline and reported the pending release as ~119 commits / 274 files / 31k additions, with two migrations needing a lock-timeout and duplicate-count protocol. The failure mode

A stale record is more dangerous than a missing one, because it is trusted. The whole migration-verification protocol had no target, and nothing in the system contradicted it.

What is already done

ReleaseDriftDetector (shipped 2026-08-02) surfaces this: it compares the running image SHA against the last succeeded deployment and reports drift, unrecorded, mixed_release or unknown, failing closed. On its first fleet run it flagged Conductor itself.

That is detection, not a cure. This slot removes the cause.

Why this is unblocked now
  • The scripts exist for exactly one reason: Conductor's registered deploy was Kamal-shaped, and a Kamal roll starts kamal-proxy on :80/:443, colliding with host Caddy on a shared box.
  • That reason has expired. ADR 0003 gave Conductor plain-docker deploys behind a host-Caddy edge with a health-checked cutover, and the fixed-port detection fix (2026-08-01) made Caddy-edge apps deployable at all.

Slices

  1. Bridge — report from the script. bin/deploy-ssdnode posts to the deploy webhook on EXIT, so failed rolls are recorded too. Committed 2026-08-03 as d4431503; deliberately temporary and deleted by slice 3.
  2. Parity audit per app. For each of the three: env file → Conductor env vars, accessory containers, host-Caddy route, published port, and the post-deploy batch (InventList runs seven backfills). Anything Conductor cannot yet express is the real work.
  3. Cut over, supervised, one app at a time. Reconfigure to deploy_method: docker on the Caddy edge, deploy through Conductor with an external probe running, clear the deploy hold last. Rollback path written before starting.
  4. Delete the scripts and the bridge reporting with them.

Sequencing note

Do the SHA-tagging first where it applies. A mutable tag means the box cannot say what commit it runs, so rollback is impossible regardless of how good the rollback code is — and that failure is silent.

Acceptance

  • All three apps report in_sync in ReleaseDriftCheckJob for a full sweep after a real deploy.
  • A deploy performed from the Conductor UI produces a deployment record with the correct SHA, and a rollback to the previous release succeeds on a canary.
  • No app deploys as root.
  • The repo scripts and the bridge reporting are deleted, not merely unused.
